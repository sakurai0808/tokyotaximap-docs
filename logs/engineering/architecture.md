## まず前提の確認

## 選択肢は実質 3 つ

WordPress の経験があると「CMS か否か」の二択に見えますが、Markdown 前提だと実際には次の 3 層になります。

**A. Git 管理（リポジトリ内に `.md` ファイル + front matter）**
記事はリポジトリの中のファイル。メタデータは front matter（YAML）で持つ。

```markdown
---
title: 東京ミッドタウン
category: 施設
wards: [港区]
keywords: [ミッドタウン, ミッドタウンビル]
pinmap: true
location: { lat: 35.6656, lng: 139.7312 }
youtube: https://youtu.be/xxxx
---

本文...
```

**B. Git ベースのヘッドレス CMS（Decap CMS / TinaCMS など）**
実体は Git 上の `.md`（=A と同じ）。その上に**編集用ダッシュボード UI**をかぶせる。プレビューやフォーム入力ができるが、保存先はリポジトリ。

**C. API ベースのヘッドレス CMS（microCMS / Contentful など）**
記事はクラウドの DB に入り、ビルド時/実行時に API で取得。Markdown で書けるものもあるが、実体は Git 外。

## あなたの直感は、この規模では正しい

「エンジニアが管理するだけなら Git のほうが AI にも読ませやすく、システムとして管理しやすい」というのは、**この案件では的を射ています**。理由:

| 観点                     | Git 管理 (A)                        | API ヘッドレス CMS (C)              |
| ------------------------ | ----------------------------------- | ----------------------------------- |
| AI への読み込み          | ◎ ファイルをそのまま渡せる          | △ API 経由で吸い出す一手間          |
| URL 引き継ぎ（移行要件） | ◎ ファイル名/slug で制御しやすい    | ○ 設定次第                          |
| 全文検索インデックス構築 | ◎ ビルド時に全 `.md` を走査するだけ | △ 一度全件取得が必要                |
| バージョン管理・差分     | ◎ Git そのもの                      | △ CMS 側の履歴機能に依存            |
| 費用                     | ◎ 無料（リポジトリのみ）            | △ 従量/月額、600 本規模で効いてくる |
| ロックイン               | ◎ ただのファイル                    | △ 製品依存                          |
| リライト運用（順次修正） | ◎ 差分で追いやすい                  | ○                                   |

特に、この案件の肝である **全文検索+サジェスト** と **AI によるリライト支援** は、記事がプレーンな `.md` としてリポジトリにある状態が圧倒的に相性が良いです。ビルド時に全ファイルを読んで検索インデックス（例: FlexSearch/Pagefind 等）を生成する、という素直な構成が組めます。

## CMS の利点（ダッシュボード）は、こう埋められる

WordPress で感じていた「わかりやすいダッシュボード」の価値は、主に次の 3 つに分解できます。そしてそれぞれ Git 運用でも代替可能です。

1. **フォーム入力でメタ data 入力ミスを防ぐ** → front matter のスキーマを Zod 等で検証、または後述の B を導入

## 検索との関係

要件を整理すると、検索インデックスに載せる情報源は 3 つあります。

| 情報源           | どこから来るか                  | 役割                               |
| ---------------- | ------------------------------- | ---------------------------------- |
| 本文全文         | Markdown 本文                   | 記事内の説明を横断検索             |
| 別名・キーワード | **front matter**                | タイトルにない呼び方・旧名称を拾う |
| ミニ単語帳       | 別ファイル（全区共通 1 ページ） | 用語検索 → 単語帳の該当箇所へ      |

front matter が検索で特に効くのは **`aliases`（別名）** あたりです。`features.md` にある「正式名称が定まっていない」「呼び方がまちまち」なケースは、本文に書いていてもヒットしにくいことがあります。意図的に登録しておく価値があります。

```7:7:docs/requirements/features.md
タクシーでは「過去に使われていた名称」や「正式名称が一般的には定義されておらず、ユーザーによって呼び方がまちまち」なものが多くある。キーワードとしてそれらの名称も登録しておくことで検索効率を上昇させる。
```

一方 **サジェスト** は要件上、候補タップで **タイトル** が検索ボックスに入ります。なのでサジェストの主データは `title` で、`aliases` は「検索実行時のヒット」向け、という分担が自然です。

```9:9:docs/requirements/features.md
サジェスト機能を導入し、検索ボックスに文字を入力している間に「（自分が知りたいのは）これかも」と思わせられるようにする。候補をタップすると検索ボックスに候補のタイトルが挿入され、すぐに検索ボタンの押下につなげられるようにする。
```

## front matter の設計方針

キーを「検索用」「表示・導線用」「地図用」に分けて考えると整理しやすいです。

### 1. 全記事共通（必須）

```yaml
---
title: 東京ミッドタウン # 表示名・サジェスト・検索（高ウェイト）
slug: tokyo-midtown # URL引き継ぎ（移行要件）
category: 施設 # カテゴリ一覧・さくいん
wards: [港区] # 区絞り込み（複数可、空配列も可）
aliases: # 検索専用の別名（本文に無くてもよい）
  - ミッドタウン
  - ミッドタウンビル
thumbnail: /images/articles/tokyo-midtown.jpg
---
```

- **`slug`** は `content-model.md` にはないですが、`migration.md` の URL 引き継ぎのために実質必須です
- **`wards`** は `[]` を許容（タクシー基礎など区なし記事）
- **`aliases`** は配列 1 本にまとめるのがおすすめ。「別名」と「キーワード」を分けると、どちらに何を書くか迷いが生じます

### 2. ピンマップ対象のみ（条件付き）

```yaml
pinmap: true
location:
  lat: 35.6656
  lng: 139.7312
summary: 六本木ヒルズ隣。赤坂方面からは… # ポップアップ用の短い概要
```

ピンマップ対象カテゴリは要件で決まっています（交差点・主要駅・施設・抜け道・知名度の高い道・首都高）。`pinmap: true/false` を明示しておくと、カテゴリから自動判定するより例外（座標未確定など）を扱いやすいです。

### 3. 任意

```yaml
youtube: https://www.youtube.com/watch?v=xxxx
publishedAt: 2026-01-15 # 将来の並び替え用（今は必須にしなくてよい）
updatedAt: 2026-07-01
```

### 実装

```ts
export type PinmapItem = {
  slug: string;
  title: string;
  category: string;
  location: { lat: number; lng: number };
  summary: string;
};

export function getPinmapItems(): PinmapItem[] {
  const pinmapItemList: PinmapItem[] = [];

  for (const slug of getAllSlugs()) {
    const { frontMatter } = readArticleFile(slug);

    if (frontMatter.pinmap) {
      pinmapItemList.push({
        slug,
        title: frontMatter.title,
        category: frontMatter.category,
        location: frontMatter.location,
        summary: frontMatter.summary,
      });
    }
  }

  return pinmapItemList;
}
```

### 学んだこと

- `map` は「1個入れたら1個出る」。`pinmap: false` の記事を捨てることはできないので、「空の箱を用意 → 1本ずつ取り出す → 条件に合えば `push` → 箱を返す」の手順で書く
- `if (frontMatter.pinmap)` の `{ }` の中でだけ、TypeScriptは `pinmap: true` の記事だとわかり、`location` と `summary` を使わせてくれる（判別可能なユニオン型の絞り込み）
- オブジェクトの `{ }` の中に書けるのは `キー: 値,` の並びだけ。`if` は文なので、関数の本体に書く
- `push( )` のかっこは「箱に入れる物を渡す口」。オブジェクトを入れるときは `push({ ... })` とかっこが2重になる
- `frontMatter` が生まれるのは `readArticleFile` の `return { frontMatter: result.data, content }`。ファイルを読む → `matter` でfront matterと本文に分ける → Zodで検証 → 名前を付けて返す、の流れ。受け取る側の `const { frontMatter } = ...` は分割代入
- オブジェクトはデータの形（名前の付いた値のまとまり）。オブジェクト指向は、データと処理をクラスにまとめて組み立てる考え方で、別物。PoCは、データはただの入れ物、処理は関数、という作り方。`配列.push()` や、Leafletの `map.setView()` のような `オブジェクト.メソッド()` は、「そのオブジェクトに仕事を頼む」と読めばよい

### つまずいた点

- `map` の形を残したまま、その中に `for` を入れていた。`for` は `map` の代わり
- 作ったばかりの空の箱を `for` で回していた（取り出す元は `getAllSlugs()`）
- `push()` のかっこが空で、オブジェクトを `return` に書いていた。`push(` の中に `{ }` で包まずに `キー: 値` を並べていた
- `location` の型を `number` にしていた（`{ lat, lng }` のオブジェクト）

- `(typeof 配列)[number]` は「その配列の中身の1つ」の型。`as const` のおかげで、11個の決まった文字列のどれか、になる。`型[]` は「その型の配列」で意味が違う

- 記事の `slug` に `area`・`search`・`pagefind`・`404` を使えないようにし、使っていたらビルドを止める

### 学んだこと

- `Record<キーの型, 値の型>` は「決まったキーが全部そろったオブジェクト」の型。キーが足りないと、オブジェクト全体（変数名）にエラーが付く。余分なキー（打ち間違い）は、そのキーにエラーが付く。打ち間違いでは「余分なキー」と「本来のキーの不足」の2つの間違いがあるのに、エラーは1つしか出なかった。1つ直したら、もう一度チェックする
- `tsx` はTypeScriptを実行する別の道具。型のチェックは `tsc`
- `generateStaticParams` が返すオブジェクトのキーは、フォルダ名 `[city]`・`params` の中の名前と同じにする。`({ city })` は `({ city: city })` の省略形で、キーと変数の名前が同じときだけ使える。型の名前 `City` とURLの部品の名前 `city` は別のもの
- `{ City: city }`（キーの打ち間違い）は `tsc` ではエラーにならず、devで開いたときに初めてエラーになる。返す型を `Promise<{ city: string }[]>` と書けば、`tsc` でも見つけられる
- `page.tsx` は `export default` でReactコンポーネントを渡すのが決まり。ないと「The default export is not a React Component」のエラーになる
- `配列.find((x) => 条件)` は条件に合う最初の1つを返し、なければ `undefined`。`filter` は合うもの全部を配列で返し、なければ `[]`
- `オブジェクト[キー]` で値を取り出す。`[ ]` の中にはキーの入った変数も書ける（`cityPaths[c]`）。`cityPaths.c` は「`c` という名前のキー」を探すのでエラーになる
- `if (!cityName) { notFound(); }` の後では、TypeScriptが `cityName` の型を `City | undefined` から `City` に絞り込む。`if` より前で `getArticleSummariesByCity(cityName)` に渡すとエラー（`TS2345`）。いっぽう `<h1>{cityName}</h1>` は `undefined` も受け付けるのでエラーにならない。受け取り口の型を書いておくと、渡し間違いを `tsc` が止めてくれる
- 関数の中で使える名前は、引数の名前と、関数の中で作った名前。ほかの関数（`page.tsx` の `city`）の変数は見えない。`frontMatter.city` の `city` はオブジェクトの部品の名前で、単独の変数ではない
- `return` より後の行は実行されない。関数の `}` の外に書いた行は、その関数の変数を使えない
- `配列.includes(値)` は、配列の要素に同じものがあれば `true`。文字列にも `includes` があり、こちらは「文字の並びが含まれるか」。`slug.includes("area")` はエラーにならずに `akasaka-area-guide` のようなslugまで当たってしまうので、箱（配列）の側から呼んでいるかを確かめる
- `as const` は、値の一覧を型として使うとき（`z.enum`、`Record` のキー）に付ける。何が来るか分からない値を照らし合わせる一覧（`reservedSlugs`）に付けると、`includes(slug)` に `string` を渡せずエラーになる
- `[]` と `"港区"` のように、配列と文字列を `===` で比べると決して等しくならない。TypeScriptは「no overlap」のエラーで止める（なければ、どの区も0本になる）
- JSXで「0本なら別の表示」は `{条件 ? (A) : (B)}`。`(` は `?` の後。`<ul>` の中に入れてよいのは `<li>` だけ
- `.map` でJSXを並べたら `key` を付ける。`key` を消しても、`tsc` もプロジェクトのESLintの設定も何も言わなかった。一覧が後から変わる場所（ピンマップの絞り込み）では、表示がずれる原因になる
- `href` の先頭の `/` は「サイトの一番上から」。`/` がないと今いる場所からになる。区のリンクに `/area` を付け忘れると `/chiyoda/` が記事のページとして扱われ、「missing param」のエラーになった
- 静的エクスポートでは、URLとファイルの置き場所が1対1（`/area/chiyoda/` → `out/area/chiyoda/index.html`）。devは開かれたページをその場で作るので、対応表にない値でもページを作ろうとする
- 記事とほかのページが同じURLを作るとき、ビルドはエラーにならず、片方だけが書き出される。ビルドのログの `Route (app)` に同じURLが2回出るのが唯一のしるし
- リロードは今いるURLを読み直すだけ。リンクを直したら、リンクのあるページに戻って踏み直す
- ターミナルの `[browser] A tree hydrated but …` は、ブラウザの拡張機能（Google Analyticsのオプトアウト）が `<html>` に属性を足したことによるもので、自分のコードの間違いではない
