# コンテンツモデル・編集方針

## 管理形式

コンテンツはMarkdownで管理する。カテゴリや記事ごとに優先すべき情報は異なるため、編集者が重要なブロックを本文の上部へ配置する。

記事URLは `https://tokyotaximap.com/{slug}/` 形式とし、パスprefixは付けない。既存WordPressサイトの英字スラッグを引き継ぐ。エリアから探す（区の一覧）のページは `/area/{英字}/` とする（[アプリケーション技術設計](../engineering/architecture.md#エリアから探す)）。

### ファイル配置

記事ファイルは **slugフラット**で置く。カテゴリ別フォルダにはしない（URLにカテゴリを含めないため。カテゴリはfront matterの `category` で持つ）。

| 段階                             | パス                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- |
| 設計サンプル（本リポジトリ）     | `docs/design/samples/articles/{slug}.md`                                      |
| 実装リポジトリ（将来）           | `content/articles/{slug}.md`                                                  |
| サムネイル画像（実装リポジトリ） | `public/images/articles/{slug}/{n}.webp`（`thumbnail` と対応。[画像](#画像)） |

設計サンプル: [ザ・キャピトルホテル東急](./samples/articles/the-capitol-hotel-tokyu.md)

## 重要ブロック

「そのページで強調すべき情報を表示したブロック」を「重要ブロック」と呼ぶ。

例:

- 施設: 車寄せの情報、住所の情報
- 交差点: 右折禁止の情報
- 首都高: 構造、周辺のエリアの情報

施設では **住所**（ナビ入力・コピペ）と **車寄せ**（運行判断）を上部の重要ブロックとする。並びは原則 **住所 → 車寄せ**（既存サイトを踏襲し、コピペしやすさを優先する）。

首都高では **構造**（路線・入口の位置）と **周辺のエリア** を上部の重要ブロックとする。並びは **構造 → 周辺のエリア**（2026-11-24決定）。

同じカテゴリでも、ドライバーの現場目線では記事ごとに重要項目の順序が異なる。このため、現時点では細かな配置ルールを定めず、記事ごとに判断する。

## 編集ルール

既存のWordPressサイトは自由に編集しながら作成されており、統一ルールが定まっていない。カテゴリ選定と本文構成の方針を以下にまとめ、カテゴリ横断の細部はサンプル記事を増やしながら言語化する。

### カテゴリ選定

1記事1カテゴリとする。同じ場所が複数の観点（通称・抜け道など）に当てはまる場合、記事の主題で1つを選び、重なりは `tags` や `keywords` で表現する。

- 場所の種類がはっきりしているもの（交差点、主要駅、施設、首都高）はそちらを優先する。
- 道について、主題が「名前の確認」なら `通称がある道`、「走り方・ルート」なら `抜け道・定番ルート` とする。
- `抜け道・定番ルート` カテゴリ内では、地点が特定しやすい抜け道は `pinmap: true`、区間が広い定番ルートは `pinmap: false` とする。

### 本文構成

記事は一般的なブログほど長くないため、見出しは `##` を基本とし、区分が増えるときに `###` を使ってよい。首都高では、ルートの区分（パターン1、2…）に `###` をよく使う（2026-11-24決定）。

- 重要ブロックのあと、本文は原則 **`## 基本事項` にまとめる**
- 内容依存の見出し（例: 「パターン1…」「入口の入り方」）は付けてよい。固定の見出し（住所・車寄せ・基本事項・地図）は、型のとおりに付ける
- 本文内の区分は太字・段落で足りる
- 地図がある場合は **`## 地図(GoogleMap)`** を置く（試験版。Googleマップを埋め込むため。2026-11-24 20:15 JST に決定。埋め込みの具体的な方法は本番までに決める）

「施設」記事の型（サンプル: ザ・キャピトルホテル東急）:

```markdown
## 住所

## 車寄せ

## 基本事項

## 地図(GoogleMap)
```

まずは施設でこの型を採用する。他カテゴリも同様に寄せる。

---

「幹線道路」記事の型(サンプル: 赤坂通り) :

```markdown
## 基本事項

## 地図(GoogleMap)
```

交差点のテーブルは、概要を記述したあとに表示させる。読者からするとページを開いていきなりテーブルが表示されても困惑する可能性があり、また概要文も長い文章になることはそんなに考えられない。また幹線道路によってテーブルの行数の多さがまちまちであることを考慮したうえでの決定である。

### カテゴリごとの型（試験版30本から。2026-11-25決定）

試験版の30本を移行して、実際に使われた見出しを、カテゴリごとにまとめた。上の「施設」「幹線道路」の型を基本にして、カテゴリ固有の見出しを足す。表の `任意` は、内容がある記事だけ置く。

| カテゴリ           | 見出しの並び                                                                                                         | `pinmap` |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- | -------- |
| 施設               | `住所` → `車寄せ` → `基本事項` → `地図(GoogleMap)`                                                                   | `true`   |
| 幹線道路           | `基本事項` → `地図(GoogleMap)`                                                                                       | `false`  |
| 交差点             | `右左折について` → `交差する主な通り`（任意）→ `基本事項` → `Uターンについて`（任意）→ `地図(GoogleMap)`            | `true`   |
| 主要駅             | `住所`（任意）→ `車寄せ`（任意）→ `基本事項` → 駅ごとの固有の見出し → `地図(GoogleMap)`                              | `true`   |
| 主要エリア解説     | 導入文（見出しなし）→ 下の「主要エリア解説の見出し」。`基本事項`・`地図` は置かない                                  | `false`  |
| 首都高             | `構造` → `周辺のエリア` → `基本事項` → `入口へ向かうパターン`（任意。`###` でパターン1、2…）→ `地図(GoogleMap)`     | `true`   |
| タクシー基礎       | 導入文（見出しなし）→ 内容依存の見出し（`###` は区分が増えるときだけ）。`基本事項`・`地図` は記事ごとに判断          | `false`  |
| 抜け道・定番ルート | `時間制限` → `ルート`（任意）→ `基本事項` → `地図(GoogleMap)`                                                       | `true`   |
| 通称がある道       | `基本事項` → `地図(GoogleMap)`                                                                                       | `true`   |

「地図(GoogleMap)」は、`pinmap: true` の記事と、幹線道路には必ず置き、本文の最後に置く。地図のあとに本文を続けない。任意の `参考` は、`基本事項` と `地図(GoogleMap)` のあいだに置く（[参考（出典）](#参考出典)）。

**交差点**

- 重要ブロックは `右左折について`（右折禁止の情報を先頭に出す）。`交差する主な通り` はその次に置く。見出しは「交差する通り」でなく「交差する主な通り」にそろえる
- `Uターンについて` は、Uターンの注意がある交差点だけ置く

**主要駅**

- 施設型を基本にする。`住所`・`車寄せ` は、駅に建物としての乗降場所があるときに置く
- 駅ごとの固有の見出し（例: `その他の改札口`、`近くの高速入口、出口`、`八重洲南口について`）は、`基本事項` と `地図(GoogleMap)` のあいだに置く
- 例外: `tokyostation-marunouchi` は、`住所`・`車寄せ` の見出しがない（北口と南口の2つのロータリーを本文で説明している）。移行の前に、見出しを足すかを決める

**主要エリア解説の見出し**

`近い首都高速の入口`（表）→ `幹線道路` → `定番ルート・抜け道`（任意）→ `知名度の高い道` → `交差点` → `施設` → `目印` または `駅`（任意）→ `その他`（任意）の順。記事のないものは、リンクなしの名前だけを書く。

**タクシー基礎**

- `city` は基本的に `[]`。特定の区に属する駅などは、その区を書く（例: `shinagawa-station` は `[港区]`）
- 本文の画像は残す。`thumbnail` は本文の最上部の画像を基本にする。全体図のように、記事を代表する画像があるときは、それでもよい（例: `about-route-c1` は `4.webp`）

**抜け道・定番ルート**

- `時間制限` は、なければ「なし」と書く（車寄せの「なし」と同じ考え方）
- `ルート` は、道順を1行で書けるときに置く。くわしい説明は `基本事項` に書く

### 引用ブロック

本文の注意や補足は、次の語を使った引用ブロック（`> **語**: …`）で書く。

| 語       | 使う場面                                 |
| -------- | ---------------------------------------- |
| `注意`   | 進入や降車で気をつけること、事故の元     |
| `方向`   | 首都高の出入口に入れる・出られる方向     |
| `ルート` | 首都高の入口へ向かう道順（パターンごと） |

### 内部リンク

本文の内部リンクは、`/slug/` の相対リンクで書く。`https://tokyotaximap.com/slug/` の絶対URLは使わない（試験版から本番のドメインへ飛んでしまうため）。

### 記事のパーツ（2026-11-25決定。実装はこれから）

WordPress（310本）で使われている、強調やリンクのパーツを、どう再現するかを決めた。集計は2026-11-25に行った（WordPressの本文のHTMLから数えた）。

| WordPressのパーツ                     | 使われている数       | 決めたこと                                                                                  |
| ------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------- |
| 枠線ブロック（VK Blocks の border-box） | 334個・184本         | `:::block[タイトル]` で書く（下の「枠線ブロック」）                                         |
| 黄色マーカー（`vk_highlighter`）      | 96個・82本           | `<mark>…</mark>` で書く（下の「黄色マーカー」）                                             |
| リンクカード（`lkc`）                 | 35個・9本            | 段落がサイト内リンク1つだけのとき、表示側が自動でカードにする（下の「リンクカード」）       |
| 赤字（`vivid-red`）                   | 106個・88本          | やめる。変換では太字にする                                                                  |
| 吹き出し（VK Blocks の balloon）      | 30個・25本           | 引用ブロック（`> **方向**:` など）にする。試験版の `iikura-entrance`・`kyobashi-exit` で実施済み |
| アラート（VK Blocks の alert）        | 2個・2本             | 廃止された出入口の記事の注意。`status: 廃止` に置き換える（下の「廃止された出入口の記事」） |
| 青い文字（`pale-cyan-blue`）          | 1439個・291本        | リンクの文字色。強調ではないので、再現しない（リンクの色はCSSで決める）                     |

太字は標準のMarkdown（`**…**`）を使う。

#### 枠線ブロック

Zennの `:::message` と同じ形で、`:::` で囲む。Markdownの読み取りには `remark-directive` を使い、自作のプラグインで `<div>` に変える。タイトルは `<h2 id="…">` として出力する（見出しとしての意味づけと、`#タイトル` のアンカーを残すため）。

```markdown
:::block[車寄せ]{type=important}
**あり**…外堀通りの呉服橋交差点向き、左側にあります
:::
```

- `[…]` はタイトル。`住所`、`車寄せ`、`右左折について`、`時間制限`、`構造`、`周辺のエリア`、`交差する主な通り`、`ルート` を使う。自由な題も書ける
- `type` は3種類。色はWordPressの枠の色に合わせる（色の具体的な値は、デザインの決定で決める）

| `type`      | 枠の色 | 意味                         | 使うタイトル（WordPressの色から）                          |
| ----------- | ------ | ---------------------------- | ---------------------------------------------------------- |
| `important` | 橙     | 運行の判断に使う情報         | 車寄せ、右左折について、周辺のエリア、ルート               |
| `reference` | 水色   | 参考の情報                   | 交差する主な通り                                           |
| `plain`     | なし   | ナビに入れる、コピペする情報 | 住所、時間制限、構造（WordPressの「所属路線」）            |

- 枠にするのは、上のタイトルのブロックだけ。`## 基本事項`・`## 地図(GoogleMap)` は、これまでどおり `##` で書く
- 「カテゴリごとの型」の表の `住所`・`車寄せ` などは、この枠線ブロックのタイトルを指す。試験版の30本は、まだ `##` の見出しで書いている。表示側の実装ができたあとに、`:::block` に書き直す
- 変換スクリプトは、WordPressの枠線ブロックを `:::block` に自動で変換できる（タイトルと色から `type` を決める）

#### 黄色マーカー

`<mark>強調したい文</mark>` と書く。表示側は、生のHTMLを残す設定にする（`rehype-raw`。許すタグは安全設定で決める）。

- 見た目は、WordPressと同じく、文字の下の約40%を塗る型。色は1種類（WordPressは `#fcb900` が84個、`#fffd6b` が6個、`#cf2e2e` が6個。色は、デザインの決定で決める）
- WordPressの `#cf2e2e`（赤）のマーカーも、`<mark>` に統一する

#### リンクカード

Markdownの書き方は変えない。段落が、サイト内の記事へのリンク1つだけ（`[タイトル](/slug/)`）のとき、表示側が自動でカードにする。

- カードのタイトルとサムネイルは、リンク先の記事のfront matterから取る（Zennで、URLだけの行がカードになるのと同じ考え方）
- 文の途中にあるリンクは、これまでどおり文字のリンク
- リンク先が、記事のない `slug` のとき（試験版の30本の外など）は、文字のリンクのままにする

#### 画像

- **書き方**: `![alt](/images/articles/{slug}/{n}.webp "キャプション")`。`title`（引用符の部分）は、表示側が画像の下の `<figcaption>` にする。キャプションは任意（WordPressでは344個・307本にあった。「西新宿の超高級ホテル」のような短い説明）
- **サムネイル**: 記事ページのテンプレートが出すので、本文の先頭に同じ画像を書かない（試験版と同じ。サムネイルのキャプションは出さない）。タクシー基礎のように、サムネイルと同じ画像を本文にも残す記事は、重複を許す（これまでの決め）
- **拡大**: 本文の画像をクリック・タップすると、大きく表示する。Markdownは変えない。表示側で作る（WordPressでは150枚で使っていた。小さい文字を読めることを最優先にするため）
- **置き方**: 本文の幅いっぱいに広げて、中央に置く。幅より小さい画像は、元の大きさのまま。幅を超えない。CSSで全部同じにする
- **alt**: 必須。空の `alt` は、ビルドで見つけて警告する（WordPressでは116個・45本が空。移行のときに記事ごとに埋める）

#### 表

- 標準のGFMの表で書く。1行目が見出し行
- セルは左寄せにする（CSSで全部同じ。WordPressは全セル中央寄せ）。`:---:` のような列ごとの指定は使わない
- セルの中の改行は `<br>` を使う

#### 改行・字下げ

- `<br>` は、どこでも使ってよい。表示側は、`rehype-raw` で生のHTMLを残し、安全設定で `br` を許す
- 段落の字下げ（行頭の全角スペース `　`）はやめる。段落は余白で分ける。変換で全角スペースを消す（WordPressで488個・269本。試験版の30本にも残っている）

#### 外部リンク

- 外部サイトへのリンク（`http`で始まるもの）は、別タブで開く（`target="_blank"` と `rel="noopener"`）。外部サイトと分かる目印をCSSで付ける。Markdownは変えない。表示側が自動で付ける
- WordPressの外部リンクは41個。うち39個は、Mapionのルート確認（「ルートはこちらをクリック」）

#### 動画（YouTube）

- YouTubeのURLを、段落に1つだけ（単独行）で書く。表示側が、埋め込み（`youtube-nocookie.com`、遅延読み込み）にする。本文の好きな位置に置ける。Zennと同じ考え方
- front matter の `youtube` は、やめる（廃止予定。コード、`schema.ts`、記事3本の書き直しは、実装のときに行う。下の「front matter の変更」を参照）
- 文の途中のリンク（`[文字](https://youtu.be/…)`）は、これまでどおり文字のリンク

#### 地図

- `## 地図(GoogleMap)` の下に、Googleマップの「地図を埋め込む」のURL（`https://www.google.com/maps/embed?pb=…`）を、単独行で書く。表示側が、`iframe` にする（遅延読み込み）。地図が2つある記事は、URLを2行書く（WordPressでは9本）
- WordPressの埋め込み196個（187本）は、すべてこの形のURL。変換スクリプトで、このURLを残す（今は捨てている）
- 地図が出なくても情報が伝わるように、記事の本文を書く（`features.md` の「軽さと端末への配慮」）

#### 参考（出典）

- 公的な資料や、確かめた情報の元は、`## 参考`（任意）に、箇条書きで書く。リンクと、確かめた日付を書く（例: `- [首都高 路線図](https://…)（確認: 2026-11-25）`）
- 位置は `## 基本事項` のあと、`## 地図(GoogleMap)` の前（地図のあとに本文を続けない決め）
- `features.md` の「元の資料へのリンクと、確かめた日付を必ず載せる」に従う

#### 標準のMarkdownのままのもの

箇条書き（入れ子もよい。番号付きは、WordPressにはなかったが、使ってよい）、斜体、取り消し線、引用ブロック、リンク、表。目次は作らない（`ui-ux.md`）。

#### 内部リンクの先に記事がない場合

リンクを残す（押すと404になる。2026-11-24の決めを、2026-11-25に確かめた）。試験版では、読者に「リンクが途切れているものがある」と伝える。

#### 記事ページの部品

- **並び**: タイトル → 日付 → サムネイル → 本文（重要ブロックから）。サムネイルは、ページの一番上（重要ブロックの前）に置く（試験版と同じ）
- **日付**: 更新日を目立たせ、公開日を小さく添える（両方表示）。「更新日時点の情報です」の注意書きは、文言と置き場所をデザインの段階で決める（`features.md`）
- **関連記事**: 最初の公開には含めない。将来検討する。本文のリンク（リンクカードを含む）と、エリア・ジャンルの一覧で回遊する
- **パンくず**: 付けない（記事に区が複数あって道順が1つに決まらない。ヘッダーのロゴでトップへ戻れる）。SEOの面は、未検討（別の項目として扱う）
- **QRコードの共有ボタン**・**目次**: 最初の公開には含めない（`ui-ux.md`・`features.md`）

#### 廃止された出入口の記事

廃止された出入口の記事は、front matter に次の3つを書く（2026-11-27決定）。

```yaml
pinmap: false
status: 廃止
abolishedAt: 2025-04
```

- **ピン**: 出さない。`pinmap: false` にする（運行中に、もう使えない出入口へ案内しないため）。`location`・`summary` は書かない
- **一覧・検索**: 残す。ジャンル・エリアの一覧と検索結果に出し、「廃止」の印を付ける（検索で見つけたとき、廃止と分かるため）
- **記事ページ**: ページの先頭に「廃止」の表示を出す。表示の文言は、`abolishedAt` から作る（「2025年4月に廃止」）。`abolishedAt` の形は `YYYY-MM`
- **タイトル**: 【※廃止済み】を残す（検索結果でも廃止と分かる。先頭の表示と二重になるが、許容する）
- WordPressでは、`dobashi-entrance`・`nishiginza_entrance` の2本が、先頭に「この記事で紹介されている場所はすでに廃止されています（2025年4月）」と書いていた。変換は、この注意を `status`・`abolishedAt` に置き換え、`pinmap: false` にする（引用ブロックに直す決めは、置き換わる）
- 「廃止」の印の形（色・文字）と、一覧での並び（新しい情報を先に出すか）は、デザインの段階で決める
- 運用の構想（首都高・ICの変更をAIが拾って通知する仕組み）と結びつけやすい。`abolishedAt` があると、廃止からの年数で確かめる作業ができる

#### front matter の変更（決定、実装前）

| キー      | 変更                                                                             |
| --------- | -------------------------------------------------------------------------------- |
| `youtube` | 廃止。YouTubeのURLを本文に単独行で書く                                           |
| `status`  | 追加（任意）。`廃止` のみ。`schema.ts`・記事ページのコードを、実装のときに直す   |
| `abolishedAt` | 追加（任意）。`YYYY-MM`。`status: 廃止` のときに書く（2026-11-27決定）       |

### 用語

- 進入方向の表現は **「右左折」** に統一する（`summary`・車寄せ・本文で揃える）
- `summary` は重要ブロックの事実と矛盾させない
- 「**車寄せ**」と「**降り場所**」は別のもの（2026-11-24 21:00 JST）。車寄せは、タクシーがつけられるよう用意された建物の乗降場所（構造としての車寄せ）。降り場所は、路上の地点（車寄せのない場所で使う）。車寄せがない施設・目印は、`## 車寄せ` に「なし」と書き、路上の降り場所は `summary` などに書く

## 1記事のつくりかた

現行のWordPressサイトでの作り方（2026-11-14に聞き取り）。

1. コンテンツにするテーマを決める
2. Illustrator（iPad版、有料）で地図をトレースしながら、重要なポイントを描き足す
3. PNGで保存する。編集用のファイルは残したまま、サイト用に新しく書き出す
4. 記事を作成する

編集用のファイルは削除しておらず、すべて残っているはず。現行の画像のうちJPEGのもの（97枚）は、イラストにはPNGが向いていると知る前に作ったものか、PNGにする設定を忘れて書き出したものが大半。

## 画像

記事の画像は、文字の入った地図のイラスト（色の数が少なく、細い線と小さい文字が多い）。読む人には高齢のドライバーが多いので、小さい文字が読めることをいちばん大事にする。

- 形式は **WebPだけ**にする。予備のPNG・JPEGは置かない（[アプリケーション技術設計](../engineering/architecture.md#画像)）
- 品質は **80**。横幅は縮めずに元のまま
- 置き場所は `public/images/articles/{slug}/{n}.webp`。`{n}` は記事ごとの順番（1始まり）。`thumbnail` はだいたい `/images/articles/{slug}/1.webp`
- 日本語の元ファイル名は使わない。記事フォルダと番号で管理する（対応表は `migration/image-map.json`）
- JPEGからWebPに変えても、JPEGで文字や線のふちに出たノイズは元に戻らない。移行のときに開いてみて、気になるものだけ、Illustratorの編集用のファイルからPNGで書き出し直してWebPにする
- 新しく作る記事も、Illustratorから書き出したPNGをWebP（品質80）に変えて、同じフォルダ規則で置く

## 検索・サジェスト

検索エンジンはPagefindを採用する。構築方式・Phase設計の詳細は [アプリケーション技術設計](../engineering/architecture.md#全文検索サジェスト) を参照。

### 検索インデックス

次を検索対象とする。

- 本文全文
- `title`
- `keywords`
- ミニ単語帳の掲載語（記事front matterとは別ファイル）

`tags` は検索インデックスには載せない（回遊・関連記事用）。

Pagefindは最終HTMLを索引化するため、front matterの `keywords` は記事テンプレートでHTMLに埋め込む（画面には出さず、`data-pagefind-meta="keywords"` で出力）。本文側は `data-pagefind-body` を付ける。

### サジェスト

`title` と `keywords` でマッチさせる。候補の表示文言は常に `title` とし、ヒット元がkeywordでもタイトルを表示する。候補をタップすると検索ボックスに `title` が挿入される。

この表示ルールはPagefind同梱UIではなく、React側で実装する。本文の語では候補に出さないため、候補は `title` と `keywords` だけから探す（実装は [アプリケーション技術設計](../engineering/architecture.md#サジェストui) を参照）。

## メタデータ（front matter）

記事のメタデータはYAML front matterで管理する。具体的なスキーマ検証は [アプリケーション技術設計](../engineering/architecture.md) で実装する。

### 必須キー

| キー          | 型                    | 説明                                                                                                                                                                                                                                                                      |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`       | string                | 記事タイトル                                                                                                                                                                                                                                                              |
| `slug`        | string                | URLスラッグ（WordPressから引き継ぎ）。英小文字・数字・アンダースコア・ハイフンだけで書く（既存の16本に `_` があるため）。1文字目は英小文字か数字（`_` や `-` で始めない）。ファイル名と一致させる。`area`・`search`・`pagefind`・`404` は使えない（どれもビルド時に検証） |
| `publishedAt` | string (`YYYY-MM-DD`) | 初回公開日。移行時はWordPressの公開日を引き継ぐ                                                                                                                                                                                                                           |
| `updatedAt`   | string (`YYYY-MM-DD`) | 内容として意味のある最終更新日。表示の正とする（Gitのコミット日は使わない）                                                                                                                                                                                               |
| `category`    | enum                  | [カテゴリ一覧](../requirements/content.md#単語系記事)                                                                                                                                                                                                                     |
| `city`        | string[]              | 所属する区。区なしは `[]`。UI上は「エリアから探す」                                                                                                                                                                                                                       |
| `keywords`    | string[]              | 呼称の揺らぎ。なければ `[]`                                                                                                                                                                                                                                               |
| `pinmap`      | boolean               | ピンマップ掲載可否。全記事で `true` / `false` を明示                                                                                                                                                                                                                      |
| `thumbnail`   | string                | サムネイル画像パス（一覧・SNS共有用）                                                                                                                                                                                                                                     |

`city` の取りうる値は次の6つ。詳細は [コンテンツ構造](../requirements/content.md#区との紐づけ) を参照。

- 渋谷区、新宿区、中央区、千代田区、港区、都心以外の区

場所が2つの区にまたがる記事は、両方を書く（例: 赤坂通りは `[千代田区, 港区]`）。両方の区のページに出る。区のページのURLでは英字を使う（`shibuya`、`shinjuku`、`chuo`、`chiyoda`、`minato`、`others`）。

日付キーについて:

- 時刻は持たない（日付のみ）
- 引用符で囲まずに `2024-04-15` の形で書く（引用符を付けると文字列として扱われ、ビルド時の検証で弾かれる）
- 新規作成時は `publishedAt` と `updatedAt` を同じ日にしてよい
- 本文を実質更新したら `updatedAt` を進める

### 条件付きキー

| キー       | 型       | 条件                                                                                                                            |
| ---------- | -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `location` | object   | `pinmap: true` のとき必須（`lat`, `lng`）                                                                                       |
| `summary`  | string   | `pinmap: true` のとき必須。ポップアップ専用の短文(記事ページには表示しない)                                                     |
| `youtube`  | string   | 任意。動画がない記事はキーを省略。動画ID（英数字・`_`・`-` の11文字。例: `tBgaVIiAO_o`）を書き、URLは書かない（ビルド時に検証）。**廃止予定**（2026-11-25決定。本文にURLを単独行で書く方式にする。[動画](#動画youtube)）。実装までは、今の形で使う |
| `tags`     | string[] | 任意。なければ `[]`。enumリストは未確定                                                                                         |
| `status`   | `"廃止"` | 任意。廃止された出入口の記事だけ。`pinmap: false` と一緒に書く（2026-11-27決定。[廃止](#廃止された出入口の記事)）             |
| `abolishedAt` | string | 任意。`status: 廃止` のときに書く。`YYYY-MM`（例: `2025-04`）。表示は「2025年4月に廃止」（2026-11-27決定）                    |

### 記述例

```yaml
---
title: ザ・キャピトルホテル東急
slug: the-capitol-hotel-tokyu
publishedAt: 2024-04-15
updatedAt: 2026-07-20
category: 施設
city: [千代田区]
keywords:
  - キャピトルホテル
  - キャピトルホテル東急
  - 赤坂東急ホテル
tags: []
thumbnail: /images/articles/the-capitol-hotel-tokyu/1.webp
pinmap: true
location:
  lat: 35.673898
  lng: 139.741400
summary: 車寄せへの入口は2つあります。両方とも右左折で進入可能です。
---
```

本文構成の例は設計サンプルを参照: [ザ・キャピトルホテル東急](./samples/articles/the-capitol-hotel-tokyu.md)

`thumbnail` は記事上部の代表画像1枚を指定する。本文に複数画像がある記事（例: タクシー基礎）も、最上部の画像をサムネイルに用いる。ただし、全体図のように記事を代表する画像があるときは、それを使ってよい（「カテゴリごとの型」のタクシー基礎を参照）。
