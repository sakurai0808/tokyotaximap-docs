# 機能要件

## 検索機能

運行中の第一導線は検索にする。検索ワードに関するコンテンツを一覧できるようにするため、本文全文を検索対象にする。運行時に初めてのビルを調べる場合は、検索を行わせることで目的の記事に素早く辿り着けるようにする。

タクシーでは「過去に使われていた名称」や「正式名称が一般的には定義されておらず、ユーザーによって呼び方がまちまち」なものが多くある。記事front matterの `keywords` としてそれらの名称も登録しておくことで検索効率を上昇させる。

サジェスト機能を導入し、検索ボックスに文字を入力している間に「（自分が知りたいのは）これかも」と思わせられるようにする。`title` と `keywords` の両方でマッチさせ、候補の表示文言は常に `title` とする。候補をタップすると検索ボックスに候補のタイトルが挿入され、すぐに検索ボタンの押下につなげられるようにする。

固定ヘッダーの検索ボックスで検索ボタンを押したあとの記事一覧ページは、サジェストから候補を入れたあとも必ず挟む。これは「目的の記事に素早く辿り着ける」目的には貢献しない。しかしブログのようなコンテンツサイトとしては一般的な挙動であり、運行中のような時間がタイトなときでもストレスをかける要因にはならないと考えているからである。

## ピンマップ

サイト内のコンテンツを地図内で一覧できる。目的のピンを選択するとポップアップが出現し、概要文、Googleマップへのリンク、当サイトの解説記事へのリンクが表示される。解説記事のリンクからは記事へ直行する。

参考: [タクシー運転手向けピンマップ（テスト）](https://sample-map-eight.vercel.app/)

掲載対象は記事front matterの `pinmap: true` とする。カテゴリごとの目安は次のとおり。

- 交差点 — 掲載する
- 主要駅 — 掲載する
- 施設 — 掲載する
- 抜け道・定番ルート — 抜け道のみ掲載（`pinmap: true`）。定番ルートは指し示す範囲が広いため `pinmap: false`
- 通称がある道 — 掲載する
- 首都高 — 出入口を掲載する

幹線道路、タクシー基礎などは運行中の使用を想定しない「読み物」であり、ピンとして表示する必要性が薄いため掲載しない。

ピンマップは第二の導線とする。検索は仕事に出たばかりの新人も対象とする一方、ピンマップは3か月程度の営業経験があるドライバー、またはそれ以降のドライバーを想定する。

例えば「◯◯ という首都高の入口から入りたいが、進行する方向によっては右折禁止ではなかったか」をすぐ確認したい場面で使用する。休憩時の俯瞰を主目的とはしないが、そのような利用を妨げるものではない。

既存サイトのカテゴリ別の記事数から、ピンは現在200〜270本、約600本に増やした時点で400〜500本と見込む（施設が約半分。既存サイトの「目印」はすべて「施設」に含める）。この量に対して、次の機能を設ける。表示の詳細は [UI・UX設計](../design/ui-ux.md#ピンマップ) を参照。

- カテゴリの絞り込み
- クラスタリング（運行中に見る縮尺ではまとめない）

一覧表示（サイドバー）は、検索と役割が重なるため現時点では設けず、本実装のデザインの段階で検討する。

## YouTube

自社チャンネルを運営する。現在の本数は30本ほど。幹線道路、施設の進入路、抜け道など、ビジュアルで覚えるのが効果的な記事に紐づけて動画を作成する。

基本的に記事ページへ動画を埋め込み、画面遷移のわずらわしさを軽減する。「無線連絡で初めて行くビルを指定された」といった停車中の場面でも、短時間で確認できるものを想定する。

ただし「幹線道路」や「交差点」カテゴリの動画などは、ゆっくり流し見することを想定し、この場面での視聴対象とはしない。

## QRコードによる共有

記事ごとにQRコードを表示し、運転手と乗客が同じURLを共有できるようにする。運転手、乗客ともにスマートフォンの利用を想定し、各社独自の車載ナビは対象にしない。

### 実際のシチュエーション

1. 乗客が乗車する。
2. 乗客が知名度のある行き先を伝えるが、運転手が分からない。
3. 停車した状態で、お互いにスマートフォンで調べる。
4. 乗客が当サイトのページを発見し、「QRコードで共有」ボタンを押して運転手に見せる。
5. 運転手がスマートフォンのカメラで読み取り、該当ページから情報を得る。

## 軽さと端末への配慮

利用者の端末の性能はまちまちで、電波の弱い場所で開くこともある（[ユーザーと利用目的](users.md#利用環境)）。Web検索の結果からすぐに開けて読めるサイトを理想とする。

- ページを軽く、文字中心に保つ。届いたらすぐ読めるよう、記事はビルド時にHTMLにする（静的エクスポート）。地図のように重いものは、要るページでだけ読み込む
- 画像は、記事の移行のときにWebP（品質80）にそろえる。横幅は、小さい文字が読めるよう元のまま。現行サイトでは画像の圧縮をしていない（[コンテンツモデル・編集方針](../design/content-model.md#画像)）
- 本実装では、Chromeの開発者ツールで遅い回線（Slow 4G）と遅いCPUをまねて確かめる
- 地図が出なくても情報が伝わる記事の作りにする。ピンマップは外部の地理院タイルに頼っており、非常時に混み合うと地図だけ出ないことがあり得る

## 非常時への備え（将来の大きなテーマ）

「非常時にも耐えうるものをつくる」を、このサイトの将来の大きなテーマとする。日本は震災や異常気象が多い。2011年の東日本大震災では、東京でも震度5強が観測され、このサイトで紹介している幹線道路は軒並み動かなくなり、歩行者であふれた。そこまでの事態には打つ手がないとしても、似たことが起きたときにプロドライバーが使える知識を発信したい。

非常時には、タクシーの使われ方そのものが変わる。

- 多数の動員がかかる職がある。夜の12時ごろに東京で強い揺れを観測した地震では、急ぎの役人を郊外の自宅から永田町・霞が関（内閣府）までお乗せしたことがある（筆者の経験）
- 1995年の地下鉄サリン事件では、築地の聖路加国際病院をはじめ、多数の病院に患者が運び込まれた。タクシーはもともと病気のときにも使われるが、このときはそうした乗客ばかりだったはず

こうしたとき、車内はどうしても緊張する。新人なら「あの首都高の出口を出てすぐ右折だよな?」「あの病院は久しぶりだけど、車寄せは◯◯通り側から入るので合ってたよな…」と不安がよぎる。乗せた直後はわからなくても、信号待ちや、路肩にしっかり寄せて調べる時間は作れる。そのときドライバー（乗客が調べてもよい）が必要な情報にできる限り早くたどり着き、自信を持ってお送りできることを大きな目標とする。検索を第一導線にしている（[検索機能](#検索機能)）のも、このためである。

- このサイトの強みは、その場で集める情報よりも、前もって準備できる知識にある。例えば警視庁は、大震災のときの交通規制を前もって公開している。病院・官公庁の車寄せや入構の向き、首都高の出口からの道順も、前もって記事にしておける
- 公的な資料は正確だが、読み取りにくいデザインや資料であることが多い。「つまりドライバーはどうすればいいの?」に言い換え、幹線道路・交差点の記事と結びつけて発信する
- 元の資料へのリンクと、確かめた日付（`updatedAt`）を必ず載せる。規制や運用が変わったときに、古い言い換えが残らないようにする
- 静的なサイトをCDN（Cloudflare Pages）で配ることは、このテーマに合っている。アクセスが急に増えても落ちにくく、1か所のデータセンターが止まっても別の場所から届く（[インフラ設計](../engineering/infrastructure.md)）
- 電波がなくても読めるよう、大事な記事を端末に保存しておく仕組み（PWA、Service Worker）を将来の候補とする

## 情報の日付と、現場の判断

記事の情報は、更新日の時点のものである。道路の規制、車寄せの運用、病院の入口などは変わることがある。

- 記事ページには更新日（`updatedAt`）をはっきり見せる
- 「この情報は記載の更新日時点のものです。現場での判断を最優先にお願いします」という趣旨の注意書きを載せる。責任を逃れるための保険としてではなく、ドライバーが現場の標識や誘導を優先して安全に判断できるようにするための発信として書く
- 文言と置き場所（記事の上部・下部、重要ブロックの近くなど）は、本実装のデザインの段階で決める（[UI・UX設計](../design/ui-ux.md)）

## データの再利用（将来の構想）

このサイトの記事を、ほかのアプリでも使える核のデータにする。front matter（`category`・`city`・`keywords`・`location`・`summary` など）がそろった記事は、そのままクイズの問題やAIの資料になる。

- 想定するもの: 記事のデータを使ったクイズアプリ、モバイルアプリ、RAG（関係する記事を探してAIに資料として渡し、それにもとづいて答えさせる仕組み）を使った「タクシー知識専用AI」
- 読むだけなら、静的エクスポートのままビルド時にJSONを書き出せる（[アプリケーション技術設計](../engineering/architecture.md#未決定事項)）。ログイン、成績の保存、管理画面からの投稿のように書き込みが要るものは、サーバーで動く仕組み（候補はRuby on RailsのAPI、置き場所はVPS）を使う
- JSONの形をほかのアプリに使わせたら、それは約束になる。キーの名前を変えると使う側が壊れるので、スキーマ（Zod）で形を守る

## ドライバー向けのデジタル地図（将来の構想）

一般の道路地図は、よくもわるくも複雑すぎる。いつかは「タクシー運転手が知っておくべき情報だけをまとめたデジタル地図」を作りたい。今のピンマップ（淡色の地図の上に、選んだ場所だけを置く）はその最初の一歩で、ピンと記事を増やすことが土台になる。

## 最初の公開の範囲

既存の約300本を移行し、次の機能で最初に公開する。範囲を絞り、早く公開して利用者の意見を得ることを優先する。

含める:

- 検索（固定ヘッダーの検索ボタン、検索モーダルとサジェスト、検索結果の一覧）
- ピンマップ（トップページのファーストビュー。カテゴリの絞り込み、クラスタリング）
- 記事ページ（重要ブロック、YouTubeの埋め込み）
- 区から探す（区ごとの記事一覧）
- PC・タブレット・スマートフォンへの対応

含めない（公開後に追加する）:

- QRコードによる共有
- さくいん
- ミニ単語帳（あわせて、ミニ単語帳の掲載語を検索の対象にすることも公開後とする）

公開時期の目安は2027年2〜3月。1週間に20時間を使う前提で、残りの作業（技術検証の残り、本実装、記事の移行、リリース）を約170〜260時間と見積もり、2〜3割の余裕を見た。意見をもらうための試験版（30本ほどを移行し、別のURLに置く）は2026年12月下旬を目安とする。見積もりは、次の機能で実際にかかった時間を見て見直す。
